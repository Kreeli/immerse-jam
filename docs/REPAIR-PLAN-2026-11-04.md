## 已完成的修复

### 安装与模型

- 新包内置固定版本 Python 3.11.18 基础归档（25,128,375 字节），来自 Astral 官方 20261026 发行；SHA-256 `67215a7bf1643e33d01b17ee3f1e91a8b0b39163746855ee02594bf0608f68b4`，下载后与官方发布摘要一致。安装使用校验后的本地归档，临时解压、自检成功后切换；自检和解压都有无进展期限。
- Beat This 原先已经内置（81,058,141 字节）。修复“目标文件存在但损坏时跳过内置副本、直接走网络”的路径；损坏副本现在可离线修复。
- 安装默认只勾选已内置的 Beat This，不再默认下载 670 MB 六轨；保留其他模型手动勾选。文案明确 Python 基础包和 Beat This 已内置。PyTorch、其他 Python 依赖和 FFmpeg 仍需联网，此包不是完整离线安装包。
- 模型 Range 探测和 Python 镜像测速不再 await 可能永不结束的流取消。单流续传校验 Content-Range 起点和总长；短文件保留断点；范围状态在同 URL 换摘要时失效。
- uv 复用前校验摘要，解压采用临时文件切换；重新准备运行环境前移除旧 ready 标记。
- JSON 原子替换对 Windows 短暂文件占用作有界退避。安装进度 INI 是观察数据，暂时写不进去不应导致下载任务失败或计时器异常崩溃。
- Gitee 尝试：未发现已打开的 Gitee 页面；访问 Gitee 返回 `net::ERR_CONNECTION_CLOSED`。本轮没有上传，没有添加未经实测的 Gitee 链接。已经完成可独立使用的内置资源方案。

### 用户编辑与文件安全

- 备注成功保存后才从队列移除，异步保存期间的新文本保留；普通编辑回写不覆盖尚未保存的备注。
- 保存失败暂停点击 / 按键触发的自动重试，保留手动重试。项目有序操作按项目 ID 刷新自己的待保存编辑，不被另一项目的失败编辑阻塞。
- 两端显示保存重试和明确确认后的放弃修改入口；放弃仅恢复当前项目到上次成功保存的版本。
- 正常退出先收尾录音、等待保存，再允许关闭。Windows 移除 2.5 秒强关，Android 双返回也走握手。失败保持窗口打开；系统强杀 / 断电仍依靠已有恢复机制。
- 批量录音导入失败只撤销本次创建的 take，保留转换期间的其他编辑。选择附件后重新读取最新工程，不回写选文件之前的旧快照。
- 导出先复制独立快照，按同一份快照计算摘要和写包；完整生成后才替换目标归档。失败保留已有备份。
- Audio Jam 附件查询补齐 SQL 的歌曲 ID 参数；迁移 / 普通项目创建失败回滚本次新目录。旧录音导入临时 WebM 在复制完成后清理。
- 桌面坏录音恢复逐条容错并保留原文件；坏条目不会阻断其他正常录音。

### 录音与播放器

- 录音启动使用可取消的生命周期和播放器归属标记，取消权限等待会释放迟到的输入流；旧项目的结束回调不再改新项目的循环 / 录音状态。
- 先 arm 再等待 take-start，收到的帧等待会话 ID 后按顺序写入，避免慢 IPC 吞掉开头。
- 曲尾开始录音先回到开头 / 循环起点。录音时统一禁止速度和移调变化，补齐 Android 滑块与移调按钮。
- 录音结束恢复循环时重新安排后续播放；play 等待 append 的期间按暂停会使此次 play 失效。
- 移除录音后根据剩余音轨重算时长，并将追加后的真实时长同步保存到项目，修复空白创作仍显示旧时长的额外问题。
- 调整录音偏移后使波形缓存失效，并重新安排正在播放的音轨；变速 seek 的错误不再被自己的取消序号吞掉。
- 按住试听覆盖取消 / 失去捕获 / 卸载，并恢复之前是否播放；双指缩放收回一指后可以继续单指拖动。

- 派生 MIDI 与 `scoreAttachmentId` 绑定，重新打开使用绑定附件；删除其他乐谱保留当前同步点。切换谱清理旧同步，两端一致。旧项目缺少附件绑定时尽量保留已有人工同步，首次打开后补绑定；无法凭旧数据恢复当年未记录的多份谱归属。
- 桌面整体偏移改用应用弹窗；同步点输入改为提交时校验，可以正常逐位输入。

- Android 当前结果的音轨混音同步写回 results；未分轨原曲可加入创作，名称与位置边界校验补齐。

- 互传发送从接收磁盘队列移出，避免同时双向发送互等；空勾选不能接收；接收开始即摘取 pending 防重复导入，导入期间关闭连接不删除该任务正读取的文件。准备发送在哈希后再核实连接代次，关闭清理逐项容错。
- Python 输出严格 JSON，处理空异常消息与非有限音频；分析 / 对齐显式关闭 memmap，验证模型异常保留原始错误；临时 PCM 放入各任务自己的目录，进程结束后清理；ONNX 检查覆盖嵌套属性与稀疏张量；worker 进度不倒退，准备音频先写临时文件再替换。

## 去重中排除或保留的判断

- “八个异步下载任务同时 rename 导致 JS 数据竞态”不能按原描述成立：当前 atomicJson 是同步调用、临时名含 UUID，同一进程事件循环不会在同步函数中途交错。真实 Windows 文件锁风险成立，现做有界重试；没有凭这份报告额外引入异步写队列。
- 报告给出的 `NUL_00_xxx.wav` 不属于 Windows 的 `NUL` 保留设备名，不能用此例直接认定导出丢数据；其他导出文件名边界仍可继续专门审计。
- 移除源分组后仍被 original / 其他引用使用的文件应保留；不能按“还有文件”批量删除项目原始媒体。
- 跟练停止录音后先继续伴奏、暂停后进入合奏回听，原先有明确行为设计；没有因报告一句“新 take 未立即发声”就改掉这一规则。
